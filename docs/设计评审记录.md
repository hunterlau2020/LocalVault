## 总体结论

目前更准确的状态是：**双本地库之间的字段级 diff/merge 骨架已经打通，但删除同步（墓碑）和并发不重叠字段的自动合并——这两项作为本项目差异化卖点的关键能力——实际上都还没有接入主流程**，且冲突解决器在"保留本地"/"手动合并"两种策略下会静默丢弃被放弃的版本，违反 SRS 明确写下的"必须"条款。这些问题都可以通过代码路径（含 grep 验证）直接确认，不是理论风险。

Phase 8–10（外部修改检测、FIDO2、真实远端存储适配器）完全未开始，意味着 SRS 中大量安全/健壮性"必须"条款目前尚未实现，这符合路线图的阶段规划，但评审时不应被"7 个 Phase 已完成"的印象误导为核心同步链路已经闭环。

## 🔴 严重问题

### 1. 删除同步（墓碑机制）完全未接入 — 已实现的墓碑系统是"孤岛代码"

- **位置**：`src/core/SyncMetadata.cpp:482`（`SyncMetadataEngine::addTombstone()`）
- **验证方式**：`grep -rn "addTombstone(" src/` 全代码库只命中函数定义本身，没有任何调用点。
- **问题**：`SyncEngine::classifyEntry`（`src/core/SyncEngine.cpp:100-119`）对"本地无、远端有"的情况一律走 `DirectApply`，`applyMerges` 会把远端条目当新条目 clone 回本地。**本地删除一个条目后执行同步，只要远端还留着旧版本，该条目会被同步流程重新"复活"**。
- **违反条款**：SRS 3.6.1（"删除条目后，系统必须保留墓碑记录"）、验收标准第 3 条（"删除生成墓碑"）。
- **连带影响**：`LifecycleManager::cleanupTombstones`（`src/core/LifecycleManager.cpp:190`）能正确清理墓碑索引，但索引永远是空的——下游功能建在一个从未被上游写入的地基上。

### 2. 并发但字段不重叠时的"自动合并"未实现，所有并发修改一律升级为冲突

- **位置**：`src/core/SyncEngine.cpp:100-209`（`classifyEntry`）、`src/core/SyncEngine.cpp:84`（`findOverlappingFields`，定义但从未调用）
- **问题**：架构 8.4 与 SRS 3.5.4 明确要求：并发修改若字段集合无交集，必须自动合并；只有同字段冲突才需人工处理。但 `SyncOperation::AutoMerge` 在 `classifyEntry` 中从未被赋值（只在 `applyMerges`/`analyzeDiffs` 的 switch 分支里作为死分支存在）。代码注释也直言不讳（`SyncEngine.cpp:181-190`）："Without a sync baseline we treat ALL differing fields as concurrent... every field is a conflict"。
- **影响**：两台设备分别只改了 `notes` 和 `url` 这种完全不冲突的场景，也会被判为冲突。
- **违反条款**：SRS 3.5.4、验收标准第 6 条（"不同字段并发修改时可自动合并"）。

### 3. 冲突解决 `KeepLocal` / `ManualMerge` 会静默丢弃被放弃版本

- **位置**：`src/core/ConflictResolver.cpp:216-224`（`resolveKeepLocal`）、`src/core/ConflictResolver.cpp:245-264`（`resolveManualMerge`）
- **根因**：`Entry::endUpdate()`（`src/core/Entry.cpp:1114-1126`）只有在 `m_modifiedSinceBegin` 为真时才把 `beginUpdate()` 时的快照写入历史。`resolveKeepLocal` 不修改任何字段，因此远端冲突版本的内容从未被写入历史或其他任何地方，直接丢失。`resolveManualMerge` 会把"合并前的本地状态"自动归档（因为字段确实变了），但远端源版本同样从未被归档。
- **对比**：`resolveKeepRemote` 是正确的——`copyDataFrom` 触发字段变化，`endUpdate` 会自动把覆盖前的本地状态存入历史。
- **违反条款**：SRS 3.4.6 第 3、5 条（"远端冲突版本不得丢失，必须保留在条目历史中"；"本地与远端两个冲突源版本都必须进入历史记录"）。
- **测试覆盖缺口**：`tests/TestConflictResolver.cpp` 中 17 个"全部通过"的用例没有一个断言 `history()` 内容，说明测试套件目前没有覆盖这条规格红线，"测试全绿"给出的信心是虚高的。

### 4. `SnapshotService::restoreSnapshot` 存在数据丢失风险

- **位置**：`src/core/SnapshotService.cpp:254-257`
- **问题**：先 `QFile::remove(originalPath)` 再 `QFile::copy(...)`，顺序不安全。如果复制失败（磁盘满、权限、中断），原数据库文件已被删除且无替代品，函数返回 `false` 但用户主数据库文件已经消失。函数前面会创建"保护快照"作为兜底，但代码没有任何提示或自动回滚路径。
- **附加问题**：恢复完成后没有重新加载内存中的 `Database` 对象。若调用方后续继续持有同一个 `db` 并调用 `save()`，会用恢复前的内存状态把刚恢复的文件重新覆盖。目前 CLI 场景下进程调用完即退出，问题不明显，但 Phase 8+ 接入 GUI 的 `SnapshotView`（架构文档 4.1 已规划）后会直接触发。
- **违反条款**：Architecture 10.4（"恢复失败不得损坏当前数据库"）、SRS 18.2。
- **建议**：改为"先复制到临时文件、校验成功后原子替换"；明确 API 契约要求调用方恢复后重新打开数据库。

## 🟡 架构层面的观察

- **删除追踪出现两套并行机制**：KeePassXC 上游已有 `Database::deletedObjects()` / `DeletedObject`（配合已有的 `Merger.cpp` 使用），本分支又引入独立的 `TombstoneRecord`。两者目前互不感知，长期看容易产生"哪个是权威删除记录"的混乱。建议在修复问题 1 时一并明确两套机制的关系（复用或明确划清边界）。
- **"远端"目前只是本地磁盘上的第二个 kdbx 文件**（CLI `sync --remote <path>`），真正的 SFTP/WebDAV 适配器、外部修改检测、FIDO2 都还未实现，符合路线图阶段规划，但会影响对"同步链路已闭环"的判断。

## 🟢 做得不错的地方

- `ConflictResolver::finalizeResolution`（`src/core/ConflictResolver.cpp:319-343`）特意从 `item.localEntry`（冲突分析时的快照）而不是 `resolveKeepRemote` 覆写后的 `localEntry` 读取本地 VV，注释解释了原因——是一个容易踩、但被正确处理的细节。
- `SnapshotRecord`/`ConflictRecord` 等的 JSON 序列化都预留了容错（`fromJson` 对非法/缺失字段有默认值兜底），符合架构中 `schema_version` 向后兼容的设计意图。
- 代码注释对已知简化点很坦诚（如"V1 省略 expiry/custom_data 字段""没有 baseline 所以保守处理为冲突"），说明作者清楚当前实现边界；只是其中部分（尤其自动合并）其实是 SRS 明确要求必须做的，不应被归为"可延后"的简化。

## 修复优先级建议

1. **墓碑接入**：在条目删除路径调用 `addTombstone`，`classifyEntry`/`applyMerges` 中判断 `isTombstone`。
2. **自动合并**：真正使用 `findOverlappingFields` 产出 `AutoMerge` 操作类型并在 `applyMerges` 中落地。
3. **冲突历史保留修复**：修复 `resolveKeepLocal`/`resolveManualMerge` 的历史丢失问题，并在 `tests/TestConflictResolver.cpp` 中补充对 `history()` 内容的断言。
4. **快照恢复加固**：`restoreSnapshot` 改为临时文件 + 原子替换，并明确"恢复后需重新打开数据库"的 API 契约。

以上第 1、2 项是这条分支存在的核心差异化价值所在，建议优先处理；第 3、4 项属于已实现功能中的正确性缺陷，风险已具体到可复现路径，建议在合并入 `develop` 或对外发布前修复。
