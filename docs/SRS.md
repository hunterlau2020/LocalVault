# 1. 引言

## 1.1 编写目的
本文档用于定义本产品的功能需求、非功能需求、数据约束、安全要求、同步规则及验收标准，作为以下工作的统一依据：

---

## 1.2 项目背景
传统密码管理产品主要分为两类：

1. **中心化服务型**
   - 提供多端同步和协作体验
   - 依赖专用服务端体系
2. **本地文件型**
   - 采用本地数据库文件保存密码
   - 服务端可仅承担存储角色
   - 但多端同步通常以整库文件为单位，缺少细粒度合并能力

本项目希望在“本地数据库 + 服务端仅存密文”的架构下，实现：

- **条目级本地同步合并**
- **字段级冲突识别**
- **删除墓碑机制**
- **数据库级快照回滚**
- **条目历史恢复**
- **FIDO2 增强解锁认证**
- **数据生命周期管理**

---

## 1.3 术语定义

| 术语 | 定义 |
|---|---|
| 数据库 | 指本地加密密码库文件 |
| 条目（Entry） | 数据库中的一个账号/凭据记录 |
| 字段（Field） | 条目内的具体属性，如用户名、密码、备注 |
| 条目级本地同步合并 | 以单个条目为最小处理单元，在客户端本地完成变更拉取、比较、合并与写回，而非依赖服务端进行整库覆盖 |
| 字段级冲突 | 同一条目中同一字段被多个设备并发修改 |
| 墓碑（Tombstone） | 删除条目后保留的逻辑删除标记 |
| 快照（Snapshot） | 同步前生成的完整数据库备份副本 |
| 版本向量 / 向量时钟 | 用于判定不同客户端修改因果关系的版本机制 |
| 外部修改 | 非本产品同步机制导致的数据库文件内容变更 |
| 同步元数据 | 用于记录条目版本、字段版本、同步状态、冲突状态的辅助信息 |
| FIDO2 密钥 | 符合 FIDO2 标准的硬件安全密钥，用于本地数据库解锁增强认证 |
| 恢复密钥包 | 在启用 FIDO2 时生成的一组离线恢复凭据，用于在 FIDO2 设备不可用时恢复数据库访问能力 |
| 数据生命周期管理 | 对快照、墓碑、历史记录等长期累积数据进行保留、清理、压缩和恢复管理的机制 |

# 2. 总体描述

## 2.1 产品目标
系统应实现如下目标：

1. 提供本地加密密码库；
2. 支持**条目级本地同步合并**，而非整库覆盖；
3. 在不同字段并发修改时支持自动合并；
4. 在同字段并发修改时禁止静默覆盖；
5. 支持删除墓碑机制；
6. 支持同步前数据库级快照与同步后回滚；
7. 支持条目历史记录与单条目恢复；
8. 服务端只存储密文数据，不参与解密；
9. 支持通过通用远程存储接口进行远端数据上传与下载；
10. 支持 FIDO2 作为数据库解锁增强认证能力；
11. 支持对快照、历史记录、墓碑等数据进行生命周期管理。

---

## 2.2 用户类型
- 个人高级用户
- 技术用户
- 希望自主管理密码库的多设备用户

---

## 2.3 运行环境

### 2.3.1 客户端
- Windows 10 / 11
- 本地文件系统
- 网络访问能力
- 支持 FIDO2 设备接入的本机环境

### 2.3.2 远端
- SFTP 服务
- WebDAV 服务
- 支持 API 形式上传/下载的云盘服务
- 支持 API 形式上传/下载的邮件服务（限备份/导入导出场景）

---

## 2.4 设计原则
- 本地优先
- 安全优先
- 不依赖中心化服务
- 严禁静默数据丢失
- 所有冲突均可追踪、可恢复
- 数据库文件不得依赖网盘自动同步目录进行直接同步
- 同步元数据必须与数据库一体化受保护
- 生命周期数据必须可控增长、可压缩、可清理、可恢复

# 3. 功能需求

## 3.1 数据库管理

### 3.1.1 新建数据库
系统应支持用户创建新的本地密码数据库。

**输入**
- 数据库名称
- 主密码
- 可选密钥文件
- 可选 FIDO2 密钥绑定
- 安全参数配置

**输出**
- 生成本地加密数据库文件
- 初始化数据库内部同步元数据
- 若启用 FIDO2，则完成本地绑定关系初始化
- 若启用 FIDO2，则生成恢复密钥包并引导用户离线保存

**约束**
- 数据库必须使用强加密算法
- 默认启用高强度 KDF 参数模板
- FIDO2 不替代数据库主加密本身，仅作为数据库解锁增强认证机制
- V1 中，FIDO2 仅用于数据库解锁，不用于高风险操作确认

---

### 3.1.2 打开数据库
系统应支持用户打开已有数据库。

**行为**
- 验证主密码 / 密钥文件 / FIDO2 策略
- 加载数据库内容
- 加载数据库内部同步元数据
- 检查数据库与元数据一致性

**异常**
- 主密码错误
- 文件损坏
- 元数据异常
- 外部修改检测触发
- FIDO2 认证失败或设备不可用
- 恢复密钥包输入无效

---

### 3.1.3 锁定/解锁数据库
系统应支持手动锁定和自动锁定。

**自动锁定触发条件**
- 空闲超时
- 系统休眠 / 锁屏
- 用户主动设置

**FIDO2 解锁要求**
- V1 中，FIDO2 仅用于数据库解锁，不用于高风险操作确认；
- 若用户启用 FIDO2，数据库解锁必须采用 **主密码 + FIDO2（AND）** 模式；
- 当 FIDO2 设备不可用时，系统应提示用户当前数据库无法按已配置策略完成解锁，并提示可使用恢复密钥包进行恢复；
- V1 不支持“主密码 OR FIDO2”模式。

**恢复机制要求**
- 若用户启用 FIDO2，系统必须在初始化时生成一个**恢复密钥包**；
- 恢复密钥包应采用用户可离线保存的形式，例如 12 个助记词；
- 恢复密钥包可在 FIDO2 设备不可用时作为恢复路径，用于重新获得数据库访问能力；
- 系统必须明确提示用户：恢复密钥包应离线保管，不得与数据库文件保存在同一位置。

---

### 3.1.4 元数据存储要求
所有同步相关元数据，包括但不限于以下内容：

- 客户端唯一标识
- 条目版本信息
- 版本向量 / 向量时钟信息
- 字段级冲突记录
- 墓碑状态
- 冲突日志
- 快照关联信息
- 同步基线信息

必须作为**专用且受保护的记录存储在 KDBX 数据库文件内部**，不得以独立文件形式作为正式存储载体。

**约束要求**
1. 元数据必须受数据库整体加密保护；
2. 元数据必须随数据库文件一起备份、迁移和恢复；
3. V1 不允许采用独立 sidecar 文件作为正式同步元数据存储方式；
4. 若数据库内部元数据损坏，系统应进入修复模式，而非静默忽略。

---

## 3.2 条目管理

### 3.2.1 条目字段
每个条目至少应支持以下字段：

- 标题
- 用户名
- 密码
- URL / APP 来源
- 备注
- 自定义字段
- 标签 / 分组

### 3.2.2 条目操作
系统应支持以下操作：

- 新增条目
- 编辑条目
- 删除条目
- 搜索条目
- 查看条目历史版本
- 恢复条目历史版本

### 3.2.3 删除操作
删除条目时，系统不得立即执行物理删除，而应创建墓碑标记。

---

## 3.3 同步管理

### 3.3.1 同步方式
系统 V1 应支持通过以下远程存储方式进行数据上传与下载：

- SFTP
- WebDAV
- 云盘 API
- 邮件 API（限备份/导入导出场景）

### 3.3.2 同步模式
V1 仅支持：
- 手动同步

说明：
- 同步动作的核心是**条目级本地同步合并**
- 服务端只提供密文存储与取回能力
- 比较、判定、Merge、冲突处理均在客户端本地完成

### 3.3.3 同步入口
系统应提供：
- “立即同步”操作入口
- 最近同步时间显示
- 最近同步结果显示
- 同步异常提示

### 3.3.4 同步目录限制
系统不得引导用户将数据库文件直接放入网盘自动同步目录中使用。

系统应：
- 提示用户将数据库保存在本地专用目录；
- 通过产品内置的远程存储接口执行上传/下载；
- 在检测到数据库位于已知自动同步目录时给出风险提示。

---

## 3.4 条目级本地同步合并

### 3.4.1 同步最小粒度
系统同步最小粒度为条目，不得以整个数据库文件作为唯一同步最小粒度。

### 3.4.2 本地合并要求
系统必须在客户端本地完成以下动作：
- 拉取远端变更
- 比较本地条目版本与远端条目版本
- 判定因果关系或并发关系
- 执行自动合并或触发冲突处理
- 将合并结果写回本地数据库

### 3.4.3 不受影响条目
未发生变化的条目在同步时不得被无故覆盖或改写。

### 3.4.4 整库覆盖限制
系统不得将“下载远端数据库并整体覆盖本地数据库”作为默认同步策略。

仅在以下场景下可进入人工确认的整库恢复模式：
- 用户主动执行快照恢复
- 数据库严重损坏
- 数据库内部同步元数据无法修复且用户确认重建

### 3.4.5 回滚粒度要求
同步前快照提供的是**数据库级别**的一键回滚能力。

若用户希望撤销某个条目的合并结果，应通过**条目历史记录恢复机制**完成，而不得依赖数据库快照进行单条目撤销。

**约束要求**
1. 快照恢复的作用范围为整个数据库；
2. 单条目恢复必须通过条目历史功能完成；
3. 界面文案中必须区分“恢复数据库快照”与“恢复条目历史版本”。

### 3.4.6 冲突解决版本生成规则
当用户在冲突处理界面中对冲突条目执行“保留本地”“保留远端”“手动合并”或“生成副本”等操作后，系统必须生成明确、可追踪的新版本结果。

**规则如下：**
1. 冲突解决后，系统必须生成一个新的条目版本，作为冲突处理结果；
2. 新版本必须记录其来源于一次冲突解决事件；
3. 若用户选择“保留本地”，则：
   - 以本地版本内容作为新版本主体；
   - 远端冲突版本不得丢失，必须保留在条目历史中；
4. 若用户选择“保留远端”，则：
   - 以远端版本内容作为新版本主体；
   - 本地冲突版本不得丢失，必须保留在条目历史中；
5. 若用户选择“手动合并”，则：
   - 以用户确认后的字段内容生成新版本；
   - 本地与远端两个冲突源版本都必须进入历史记录；
6. 若用户选择“生成副本”，则：
   - 原条目保留一个解决结果版本；
   - 冲突副本必须生成新的条目唯一标识；
   - 副本与原条目之间必须保留冲突关联关系；
7. 冲突解决不得直接覆盖并删除任一冲突源版本。

---

## 3.5 冲突检测与合并

### 3.5.1 判定机制
系统不得单纯依赖设备时间戳作为变更新旧判定依据。

系统必须支持：
- 客户端唯一 ID
- 版本向量 / 向量时钟或等价机制

### 3.5.2 因果关系判定
若某版本在因果关系上晚于另一版本，则可直接替换旧版本。

### 3.5.3 并发关系判定
若两个版本为并发修改，则进入冲突处理流程。

### 3.5.4 自动合并条件
仅当以下条件同时满足时，系统可自动合并：
- 为同一条目
- 两端修改字段集合无交集
- 不涉及删除冲突

### 3.5.5 严禁自动覆盖条件
���现以下任一情况时，系统不得自动覆盖：
- 同一字段被并发修改
- 删除与修改冲突
- 版本关系无法确定
- 数据库内部元数据与数据库内容不一致

### 3.5.6 冲突结果处理
冲突发生时，系统必须支持：
- 生成冲突记录
- 生成副本（本地 / 远端）
- 用户手动选择保留版本
- 用户手动编辑合并

---

## 3.6 删除墓碑机制

### 3.6.1 墓碑要求
删除条目后，系统必须保留墓碑记录。

### 3.6.2 同步规则
若远端存在墓碑，而本地存在该条目后续修改，系统必须提示用户：
- 保持删除
- 恢复条目
- 生成冲突副本

### 3.6.3 物理清理
V1 不要求支持自动物理清理墓碑。

---

## 3.7 快照与恢复

### 3.7.1 同步前快照
每次执行以下操作前，系统必须自动创建本地快照：
- 全量同步
- 批量合并
- 冲突批处理
- 修复模式执行前

### 3.7.2 回滚
系统应支持用户回滚到某个历史快照。

说明：
- 快照恢复为数据库级恢复；
- 条目级恢复不通过快照实现，而通过条目历史版本恢复实现。

### 3.7.3 历史记录
每次条目修改、合并、恢复、删除、冲突解决后，应保留历史版本记录。

---

## 3.8 外部修改检测

### 3.8.1 检测要求
系统应检测以下情况：
- 数据库文件内容被外部工具替换
- 数据库内部元数据与数据库内容不一致
- 数据库文件被放置于高风险自动同步目录

### 3.8.2 用户提示
检测到外部修改后，系统必须提示：
- 存在外部修改风险
- 当前同步状态可能不可信
- 可选择进入修复流程或中止同步

### 3.8.3 修复机制
系统应支持至少一种修复方式：
- 重建内部索引
- 识别为新分支 / 新基线
- 要求用户确认后重新绑定同步关系

---

## 3.9 数据生命周期管理

### 3.9.1 快照生命周期管理
系统必须支持对本地快照进行生命周期管理，以避免因频繁同步导致大量快照长期堆积并占用磁盘空间。

**要求**
1. 系统应支持查看快照列表、快照大小和创建时间；
2. 系统应支持用户手��删除指定快照；
3. 系统应支持按保留策略自动清理快照，例如：
   - 保留最近 N 个快照；
   - 保留最近 N 天的快照；
4. 自动清理前，系统应避免删除当前数据库最近一次可用恢复点；
5. 若快照仍被正在进行的恢复流程引用，则不得清理。

### 3.9.2 历史记录与墓碑增长管理
由于使用历史记录与墓碑机制，数据库内容会随着时间推移持续增长。

系统应支持：
1. 查看历史记录和墓碑占用规模；
2. 手动清理指定条目的历史记录；
3. 手动清理已满足条件的墓碑；
4. 在清理前明确提示数据不可逆影响；
5. 清理操作前必须自动创建数据库快照。

### 3.9.3 数据库压缩 / 清理功能
系统应提供手动执行的数据库压缩或清理功能，用于减少因历史记录、墓碑和冗余元数据累积造成的数据库膨胀。

**要求**
1. 压缩 / 清理为用户显式触发操作，V1 不要求自动执行；
2. 压缩 / 清理前必须自动创建数据库快照；
3. 压缩 / 清理完成后，系统应校验数据库完整性；
4. 压缩 / 清理失败时，不得损坏原数据库。

# 4. 数据需求

## 4.1 条目数据结构
每个条目至少应包含：
- 条目唯一标识
- 基础字段
- 历史版本标识
- 删除状态

## 4.2 同步元数据
同步元数据至少应记录：
- 客户端唯一 ID
- 条目版本信息
- 字段级版本信息或等价变更指纹
- 版本向量 / 向量时钟信息
- 墓碑状态
- 冲突状态
- 最后同步基线
- 数据库完整性校验信息

## 4.3 数据一致性要求
- 数据库内容与数据库内部同步元数据必须可交叉校验；
- 若校验失败，系统不得直接继续同步。

---

# 5. 安全需求

## 5.1 数据加密
系统必须满足：
- 本地数据库采用强加密；
- 支持 Argon2id；
- 支持 AES-256 或等价级别加密方案；
- 服务端仅存储密文。

## 5.2 身份验证与访问保护
系统应支持以下本地解锁保护方式：

- 主密码
- 密钥文件（可选）
- FIDO2 密钥（可选，V1 限数据库解锁）

### 5.2.1 FIDO2 支持要求
V1 中，系统应支持将 FIDO2 密钥用于数据库解锁增强认证。

### 5.2.2 FIDO2 模式约束
V1 中，若启用 FIDO2，则数据库解锁必须采用 **主密码 + FIDO2（AND）** 模式。

系统必须满足：
1. FIDO2 不替代主密码及其 KDF 派生加密模型；
2. FIDO2 不用于高风险操作确认；
3. FIDO2 不作为服务端认证机制；
4. FIDO2 不可用时，系统必须提供明确错误提示与恢复指引。

### 5.2.3 恢复密钥包要求
若用户启用 FIDO2，系统必须生成恢复密钥包，并满足以下要求：
1. 恢复密钥包应可由用户离线保存；
2. 恢复密钥包应采用人类可抄录的形式，例如 12 个助记词；
3. 恢复密钥包不得默认明文保存在数据库旁边或自动同步目录中；
4. 恢复密钥包的使用必须有清晰、独立的恢复流程；
5. 系统必须提醒用户：恢复密钥包拥有高权限，泄露将带来严重安全风险。

## 5.3 明文边界
系统必须保证：
- 明文只在客户端本地短暂存在；
- 服务端不接触明文；
- 日志中不得记录明文密码。

## 5.4 元数据泄露控制
V1 最低要求：
- 条目标识不得直接暴露业务语义；
- 不得上传明文条目名称、URL、用户名；
- 同步元数据尽量加密存储。

## 5.5 内存安全
处理敏感字段时，系统必须：
- 在 Merge 完成后执行安全擦除；
- 避免将明文密码保留在普通字符串对象中；
- 防止敏感数据进入调试日志；
- 对 FIDO2 交互过程中产生的敏感中间态进行同等级别保护；
- 对恢复密钥包的输入、显示、复制等过程采用同等级别敏感数据保护。

---

# 6. 并发与离线要求

## 6.1 并发上传
在无中心化协调服务端前提下，系统必须能处理多个客户端接近同时上传的情况。

**要求**
- 上传前检查远端基线；
- 若本地基于过期版本上传，则必须转入拉取与冲突处理流程；
- 不得盲目覆盖远端版本。

## 6.2 长时间离线
若客户端长时间未同步后重新上线，系统必须：
- 优先拉取远端变更；
- 分析版本关系；
- 对高风险冲突进行显式提示。

---

# 7. 交互需求

## 7.1 冲突提示界面
系统必须在冲突界面中显示：
- 条目名称
- 冲突字段
- 本地版本内容
- 远端版本内容
- 来源设备标识
- 处理选项

## 7.2 删除冲突界面
系统必须提供删除冲突提示及恢复选项。

## 7.3 外部修改风险提示
系统必须在检测到高风险状态时中断默认同步流程，并要求用户确认。

## 7.4 FIDO2 恢复引导
若用户启用 FIDO2，系统必须在初始化完成后明确展示恢复密钥包引导，包括：
- 恢复密钥包的用途说明；
- 离线保存建议；
- 风险提示；
- 用户确认已完成保存的步骤。

---

# 8. 非功能需求

## 8.1 安全性
- 不允许静默数据丢失；
- 不允许服务端可解密；
- 必须支持回滚；
- 必须支持内存安全擦除。

## 8.2 可靠性
- 同步失败不得损坏数据库；
- 冲突处理失败不得覆盖原数据；
- 回滚操作必须可用；
- 生命周期清理失败不得破坏原始数据。

## 8.3 性能
V1 目标：
- 常规数据库加载时间可接受；
- 单次同步在普通网络条件下可完成；
- 不要求实时同步；
- 生命周期管理操作不应阻塞基础查看操作过长时间。

## 8.4 可维护性
- 同步模块与数据库模块解耦；
- 远程协议适配层可扩展；
- 冲突规则应具备可测试性；
- 生命周期管理策略应可配置和可扩展。

---

# 9. 约束条件

## 9.1 技术约束
- 以本地数据库为核心；
- 服务端不负责解密与协调；
- 同步元数据必须存储在 KDBX 内部；
- 不将数据库直接托管给自动网盘同步目录。

## 9.2 产品约束
- V1 仅支持 Windows；
- V1 以手动同步为主；
- V1 的 FIDO2 仅用于数据库解锁；
- V1 不提供复杂团队共享功能；
- V1 的数据库压缩 / 清理功能以手动触发为主。

---

# 10. 验收标准

## 10.1 功能验收
系统应满足：
1. 可创建和打开本地数据库；
2. 可新增、编辑、删除条目；
3. 删除生成墓碑；
4. 可进行条目级本地同步合并；
5. 同字段并发修改时触发冲突提示；
6. 不同字段并发修改时可自动合并；
7. 同步前生成数据库级本地快照；
8. 可回滚到数据库快照；
9. 可通过条目历史恢复单条目版本；
10. 检测外部修改；
11. 服务端不接收明文；
12. 支持 FIDO2 解锁增强认证；
13. FIDO2 在 V1 中仅用于数据库解锁，不用于高风险操作确认；
14. 同步元数据存储在 KDBX 内部，而非独立文件；
15. 支持快照生命周期管理；
16. 支持手动清理历史记录或墓碑；
17. 支持手动数据库压缩 / 清理功能；
18. 启用 FIDO2 时生成恢复密钥包。

## 10.2 安全验收
系统应满足：
1. 支持 Argon2id；
2. 日志不含明文密码；
3. Merge 后敏感缓存被清理；
4. 同步元数据不暴露明文业务字段；
5. FIDO2 启用后，可按策略完成本地解锁增强认证；
6. FIDO2 不可用时，系统有明确错误提示与恢复指引机制；
7. 恢复密钥包生成、显示、输入过程受敏感数据保护。

## 10.3 异常验收
系统应满足：
1. 网络中断不会损坏本地数据库；
2. 冲突处理取消不会覆盖原始数据；
3. 外部替换数据库后会触发风险提示；
4. 删除与修改冲突时可恢复条目；
5. 元数据损坏时不会静默继续同步；
6. 快照清理失败不会损坏当前数据库；
7. 数据库压缩 / 清理失败不会破坏原始数据库。

# 11. V1 范围结论

V1 必须实现：
- Windows 客户端
- 本地数据库
- 条目级本地同步合并
- 冲突检测
- 删除墓碑
- 数据库级快照恢复
- 条目级历史恢复
- 外部修改检测
- 安全与隐私基础保障
- FIDO2 基础支持
- 恢复密钥包机制
- 快照生命周期管理
- 历史记录 / 墓碑手动清理
- 数据库压缩 / 清理功能
- SFTP / WebDAV / 云盘 API / 邮件 API 接入能力

V1 不实现：
- 浏览器自动填充
- 团队协作
- 中心化协调服务
- 自动网盘目录同步
- 移动端正式版本
- 高风险操作 FIDO2 二次确认
- 自动物理清理墓碑

# 12. 附录：关键决策摘要

1. 不采用整库文件覆盖作为主同步策略；
2. 采用**条目级本地同步合并**；
3. 不依赖时间戳判定冲突；
4. 同字段并发修改必须手动解决；
5. 删除必须使用墓碑；
6. 同步前必须创建数据库级快照；
7. 单条目恢复通过历史版本完成，而非快照；
8. 必须保留历史记录；
9. 必须检测外部修改；
10. 必须控制元数据泄露；
11. 必须保证 Merge 过程内存安全；
12. 禁止将数据库直接放入自动网盘同步目录；
13. 同步元数据必须内嵌于 KDBX 内部；
14. FIDO2 仅作为 V1 的数据库解锁增强认证机制，且采用 **主密码 + FIDO2（AND）** 模式；
15. 启用 FIDO2 时，必须提供恢复密钥包机制；
16. 快照、墓碑、历史记录必须纳入生命周期管理。
